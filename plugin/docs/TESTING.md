# Testing

How tests are written in an app built on the kit. The rules here are what the `feature-builder`
agent follows and the `code-reviewer` agent checks. `EFFECT_PRIMER.md` explains the Effect
testing helpers; this document says what to test, what not to, and what a good test looks like.

## The one rule

A test proves one behaviour that a user, a caller or a migration would notice if it broke. If
nobody would notice, the test is not worth its maintenance. If two behaviours are in one test, a
failure does not say which one broke.

Corollaries:

- Assert the observable result: the value returned, the row in the database, the error tag, the
  state after the action. Never assert that a function "was called with" something; that tests
  the wiring, and the wiring is what refactors change.
- Every failure path gets its own test, and that test also asserts what did not happen (the row
  was not written, the second step did not run).
- Never mock the unit under test, and never test a library (Effect, TanStack Query, zustand).

## Where tests live and how they are named

- `__tests__/` next to the code, one file per subject: `useCases/__tests__/renameItem.test.ts`,
  `data/repositories/__tests__/itemRepositoryLive.test.ts`. Jest finds `**/__tests__/**/*.test.{ts,tsx}`.
- One `describe` per unit (a use case, a repository method group, a store, a ViewModel). One
  `it` per behaviour, named in plain words that read as a sentence after the subject:
  `it('renames the item and keeps its other fields')`, `it('fails with ItemNotFound for an unknown id')`.
- No banner comments, no `// Arrange` / `// Act` / `// Assert` labels: the blank lines between the
  three parts carry the structure. A comment explains only a non-obvious why, as a `// NOTE:` codetag.
- Tests live inside the layer they test, so the architecture rules apply to them: a use case test
  never imports a Live Layer, a `ui/` test never imports `effect`.

## Fixtures: builders with a complete base

Every entity has a builder: a function that returns a complete, valid, realistic object and
accepts overrides.

```ts
const anItem = (overrides: Partial<Item> = {}): Item => ({
  id: ItemId.make('item-1'),
  name: 'Milk',
  createdAt: 1_700_000_000_000,
  ...overrides,
});
const someItems = () => [anItem(), anItem({ id: ItemId.make('item-2'), name: 'Bread' })];
```

- Naming: `a` / `an` / `some` plus the type: `anItem`, `aRoutine`, `someExercises`.
- The base is complete and passes the entity's Schema; `strict` TypeScript enforces the shape,
  a test in `domain/` enforces the Schema (`Schema.decodeUnknownSync(Item)(anItem())`).
- Values are realistic (`'Milk'`, not `'string'`); ids are branded through the Schema
  constructor, never raw strings.
- A builder used by one file sits at the bottom of that file, below the tests. The moment a
  second file needs it, it moves to `<feature>/__fixtures__/builders.ts`. Never hand-roll an
  object literal where a builder exists.
- External formats (an export file, a watch envelope, a catalog payload, an HTTP response) are
  fixture files under `__fixtures__/`, captured from real output and committed. A fixture is never
  regenerated by the code under test: a format test proves the code still reads and writes what
  the outside world already has.

## Doubles: Layers, not mocks

A dependency is a service behind a `Context.Tag`, so its test double is a plain object that
satisfies the interface, provided as a Layer. No `jest.mock`, no spies, no mocking library.

```ts
const ItemRepositoryFake = (items: Item[] = []) =>
  Layer.sync(ItemRepository, () => {
    const byId = new Map(items.map(item => [item.id, item]));
    return {
      list: Effect.sync(() => [...byId.values()]),
      byId: id => Effect.sync(() => byId.get(id)),
      save: item => Effect.sync(() => void byId.set(item.id, item)),
      remove: id => Effect.sync(() => void byId.delete(id)),
    };
  });
```

- A fake holds state in a `Map` or an array so a test can assert the result through the same
  interface the code uses (`repo.byId(id)` after `save`), not through a captured call.
- A fake that must fail returns `Effect.fail(new SqlError({ ... }))` for the one method under
  test; the rest stay real.
- Shared fakes for core services live in `features/core/testing` (`makeCoreTestLayer`: node
  sqlite, test clock, collected logs, a fake haptics or notifications service); feature fakes live
  next to the feature's builders.
- `jest.mock` is allowed only for a native module that crashes under Node and has no Tag
  (`expo-router`, `expo-haptics`, `react-native-reanimated`), through the manual mocks in
  `__mocks__/` at the app root, never inline in a test.
- Time: `itEffect` runs with Effect's `TestClock`, so time stands still until the test calls
  `advanceClock`. Never `jest.useFakeTimers` in an Effect test; never `Date.now()` in code that a
  test needs to control (it reads `Clock`).
- Randomness and ids: generated through a service (`Clock`, an `IdGenerator` Tag) so a test
  provides a fixed one.

## What each layer proves

| Layer | The test proves | The test never |
|---|---|---|
| `domain/` | pure rules on fixtures: the happy case, each boundary (empty list, zero, the maximum), invalid input; Schema decode and encode round-trip on a valid fixture and rejection of an invalid one | imports a Layer or touches I/O |
| `useCases/` | the outcome on the fake repository's state and the tagged error on every failure path, with `Effect.either` | asserts a call was made; imports `data/` |
| `data/` | the Live Layer round-trips through real SQL on `makeNodeSqliteLayer` (save then read, update, delete, ordering, filters); a migration reaches the current version from an empty database and from the previous version's fixture; a failing step leaves `user_version` untouched | mocks the driver or asserts SQL text |
| `state/` | one test per action on the reducer or store: the state after it, from a known state | renders a component |
| `facades/` | the runtime boundary with `renderHook`: data arrives typed, a tagged failure arrives as `error` with its `_tag`, a defect becomes `UnexpectedError`, and the fiber is interrupted on unmount | re-tests the use case's rules |
| `ui/` | the ViewModel (`.logic.ts`) with `renderHook` and a test runtime: `state` and `derived` for given facade results, `effects` change state as expected | renders a `.tsx`; pixels and native controls are device QA's job |
| formats | byte-for-byte: encoding a fixture entity equals the committed file, decoding the file equals the fixture entity | regenerates the fixture |
| hook-based repositories | nothing at unit level (Convex, Clerk and other hook-only SDKs are covered by device and web QA); the Effect wrapper around a mutation is tested with a fake mutation function that resolves or rejects | mocks the SDK's React internals |

A use case test with `Effect.either`:

```ts
itEffect(
  'fails with ItemNotFound for an unknown id and writes nothing',
  Effect.gen(function* () {
    const result = yield* Effect.either(renameItem(ItemId.make('missing'), 'New name'));

    expect(result._tag === 'Left' && result.left._tag).toBe('ItemNotFound');
    const repo = yield* ItemRepository;
    expect(yield* repo.list).toEqual([]);
  }),
  ItemRepositoryFake(),
);
```

A ViewModel test. A file-level helper that renders the hook with a test runtime and waits for
the first load keeps each test down to its own three parts:

```ts
const renderLogic = async () => {
  const runtime = makeTestRuntime(ItemsLive);
  const rendered = await renderHook(useItemListPageLogic, { wrapper: makeTestWrapper(runtime) });
  await waitFor(() => expect(rendered.result.current.state.isLoading).toBe(false));
  return { ...rendered, runtime };
};

it('submits the draft, lists the item and clears the draft', async () => {
  const { result, runtime } = await renderLogic();

  await act(async () => result.current.effects.setDraft('Milk'));
  await act(async () => result.current.effects.submit());

  await waitFor(() => expect(result.current.state.items.map(item => item.name)).toEqual(['Milk']));
  expect(result.current.state.draft).toBe('');
  await runtime.dispose();
});
```

## Async and errors

- A test body that is an Effect uses `itEffect`; it fails with the Effect's failure or defect, so
  there is no `try/catch` in a test.
- To assert a failure, use `Effect.either` (or `Effect.flip` when only the error matters) and
  check `_tag`. Never assert on the message text: messages are for logs.
- A hook test wraps every action in `await act(async () => ...)` and awaits results with
  `waitFor`; it never sleeps.
- Every test that builds a runtime disposes it (`await runtime.dispose()`), otherwise fibers leak
  into the next test.

## Coverage

The kit's jest preset sets global floors that apply when jest runs with `--coverage`
(`npm run test:coverage`, which the PR checks run after `npm run check`): 70 percent of lines,
functions and statements, 55 percent of branches, over everything the measurement includes.

Excluded from the measurement: `*.tsx`, `*.style.ts`, `index.ts`, `pages.ts`, `di/`,
`libraries/` (third-party and native wrappers such as the expo-sqlite adapter, which cannot run
under Node), `__fixtures__/`, `__mocks__/`, `app/`, `features/core/testing/`.

The floors are global on purpose: a per-file floor fails a four-line DTO with one untested branch.
They catch a feature that shipped without tests, nothing more. What the reviewer checks is the
table above: every use case, every Live repository and every ViewModel has its tests, and every
failure path is reached. A line covered by a test that asserts nothing counts for nothing.

## What is deliberately not unit-tested

- Rendering of `.tsx` files, native controls, layout, colours, animation: the `qa-engineer`
  agent drives the app on a device.
- Navigation flows across screens: device QA.
- Hook-based SDK repositories (Convex, Clerk): device and web QA.
- Bootstrap wiring (`AppLayer`, the runtime provider): the app booting on the device is the test.

## The reviewer's checklist

A test is blocked in review when any of these is true:

1. It asserts a call (`toHaveBeenCalledWith`) instead of a result.
2. It mocks the unit under test, or uses `jest.mock` for something that has a Tag.
3. A failure path exists in the code (an error tag, a branch) with no test that reaches it.
4. A fixture is a hand-rolled object literal where a builder exists, or a builder's base is
   incomplete.
5. Time or ids are uncontrolled (`Date.now()`, `Math.random()` reachable from the test).
6. Two behaviours share one `it`, or the name does not say the behaviour.
7. A format test regenerates its fixture from the code under test.
8. A runtime is created and not disposed, or a hook test sleeps instead of `waitFor`.
9. Rendering a `.tsx` in a unit test.
10. A snapshot test.
